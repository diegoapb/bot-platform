## 2. El insight: E13/E14 ya es "casi" infra-as-code

El modelo destino tiene las tres propiedades que exige una infra declarativa, **sin que sea su objetivo explícito**:

1. **Declarativo** — todo es estado deseado: entidades + relaciones N:M + reglas de ruteo como JSON puro serializable.
2. **Idempotente** — `unique constraints` + `ON CONFLICT DO NOTHING` + migraciones idempotentes + "referencia viva". Es exactamente lo que un `apply` necesita.
3. **Aislado por tenant** — la frontera de seguridad ya es consistente en todas las tablas.

**Lo que falta** para cerrar el círculo "envío un YAML y se monta todo":

- **Identidad lógica estable.** Hoy las FKs son UUIDs generados. Un YAML necesita nombrar `agent: ventas` y que el reconciliador resuelva/cree el UUID → hace falta una columna `key`/`slug` por (tenant, recurso).
- **Manifiesto + validador + motor de `apply/plan`.** No existen todavía.
- **Secretos seguros.** Hoy `channels.credentials` (jsonb con botToken de Telegram, tokens de Meta) y los webhook tokens están **en texto plano**, sin `crypto`/vault/KMS (lo confirmé en `apps/backend/src/db/schema.ts` y `package.json`). Las keys de LLM/Evolution/Chatwoot son **globales de plataforma** vía `env` (`apps/backend/src/env.ts`), no por-tenant.
- **Recursos no 100% declarativos.** La conexión WhatsApp/Evolution exige **escanear un QR**; Meta exige **OAuth**. Eso no se "monta" con texto — necesita un estado `pending` + handshake fuera de banda.

## 3. Diseño propuesto (3 piezas)

**A) Manifiesto `agentpack.yaml`** — un documento por tenant, versionable en git, referencias por `key` lógico (no UUID) y secretos/vars por interpolación:

```yaml
version: 1
tenant: acme

knowledge:
  - key: faq-tecnica
    sources: [{ kind: file, path: ./kb/faq.md }]

agents:
  - key: garantias
    model: ${vars.LLM_MODEL}        # variable no secreta
    identity:
      soul: ./identity/garantias.soul.md
      guardrails: "Escala a humano si hay frustración."
    knowledge: [faq-tecnica]        # referencia por key

channels:
  - key: wa-soporte
    type: whatsapp_evolution
    # credenciales no van aquí: se referencian
    secretRef: ${secrets.WA_SOPORTE}
    routing:
      default: garantias
      rules:
        - priority: 10
          when: { op: eq, field: { var: stage }, value: post_sale }
          agent: garantias
      orchestrator:
        enabled: true
        instructions: "Elige el agente según la etapa del cliente."
        candidates: [garantias]
```

El bloque `routing.rules[].when` es **literalmente el DSL de `routing_rules.condition` de US-036** — reuso directo, ya está tipado.

**B) Reconciliador idempotente** — `POST /api/iac/apply`:
1. Parsea YAML → valida con **Zod** (reusa el tipo `Condition` de E14).
2. Resuelve `key` → UUID con upsert por `(tenantId, key)`.
3. Calcula un **plan** (`create/update/delete`); con `dryRun` encaja con el **simulador de ruteo de US-039**.
4. Aplica en transacción respetando los invariantes ya definidos (destino candidato, default candidato, etc.).
5. Devuelve acciones manuales pendientes (escanear QR, completar OAuth) para los recursos con handshake.

**C) Bóveda de secretos + variables**:
- Tabla `secrets(tenantId, key, ciphertext, nonce, version)` — nunca en claro, nunca al frontend.
- **Envelope encryption AES-256-GCM** con `crypto` nativo de Node + `SECRETS_MASTER_KEY` (DEK por tenant cifrada con la master). Cero dependencias nuevas; migrable a Vault/KMS.
- Resolución `${secrets.X}` / `${vars.Y}` **en runtime** (al construir el cliente/contexto), nunca se persiste descifrado.
- Migrar `channels.credentials` y webhook tokens a la bóveda cifrada.

## Lo esencial

**El hallazgo central:** E13/E14 ya te dejan a un paso de "agents-as-code". El modelo destino es **declarativo** (entidades + N:M + reglas como árbol JSON), **idempotente** (`unique` + `ON CONFLICT` + migraciones repetibles + referencia viva) y **aislado por tenant**. Eso es justo lo que un `apply` necesita. El DSL de `routing_rules.condition` (US-036) ya está tipado y validado con `compileCondition` — el manifiesto lo reusa tal cual.

**Lo que falta** (la brecha real): identidad lógica (`key`/slug en vez de UUID), el manifiesto + validador, el motor `plan/apply`, y —lo más urgente— **gestión segura de secretos**. Hoy `channels.credentials` y los webhook tokens están **en texto plano**, sin `crypto`/vault en el proyecto. Por eso en el doc insisto: la bóveda de secretos es **prerrequisito**, no un añadido posterior.

**Recomendación de gestor** (tu decisión D1 fue "secret manager externo"):

| | Veredicto |
|---|---|
| **Infisical** | **Primario** — MIT, 96.8% TypeScript (afín a tu equipo), Postgres (ya lo tienes) + Docker Compose en Dokploy, SDK Node, machine identities. |
| **OpenBao** | **Alternativa fuerte** — MPL-2.0, **namespaces multi-tenant gratis en OSS** (en Vault son Enterprise de pago), secretos dinámicos/transit. Más ops. |
| Vault | Descartado para self-host: namespaces de pago + licencia BSL (IBM). |

**Patrón multi-tenant:** 1 Clerk org → 1 unidad de aislamiento (project en Infisical / namespace en OpenBao). El backend autentica como *machine identity*, resuelve `${secrets.X}` **en runtime** con caché TTL, y **nunca** persiste el valor ni lo manda al frontend. Tu DB solo guarda un índice de metadatos (`secret_refs`), no valores.
